OrynWsl 0.5.46 Quick Start

This package is a WSL-native Oryn SDK baseline.

Expected workspace layout:

  ~/OrynSDK/
    OrynSDK/
    OrynProjects/

The SDK lives here:

  ~/OrynSDK/OrynSDK

The default Kernel-5 project lives here:

  ~/OrynSDK/OrynProjects/Kernel-5/Project.oryn

Build happens inside WSL Ubuntu using Clang and LLD.
Run launches your Windows qemu-system-x86_64.exe from the WSL terminal.

You can launch from the workspace root:

  cd ~/OrynSDK
  ./Oryn.sh

Or from the SDK root:

  cd ~/OrynSDK/OrynSDK
  ./Oryn.sh

Both launchers default to:

  ~/OrynSDK/OrynProjects/Kernel-5/Project.oryn

Install tools in WSL Ubuntu:

  sudo apt update
  sudo apt install -y clang lld llvm ovmf unzip

Run the default Kernel-5 project:

  cd ~/OrynSDK
  ./Oryn.sh run

Check tools:

  ./Oryn.sh doctor

Show the version:

  ./Oryn.sh version

Build Kernel-5:

  ./Oryn.sh build

Create the FAT32 partition disk image:

  ./Oryn.sh image

Run Kernel-5 using Windows QEMU from WSL:

  ./Oryn.sh run

The native tool is created here when needed:

  ~/OrynSDK/OrynSDK/Common/Bin/oryn

You can still call it directly after it exists:

  ~/OrynSDK/OrynSDK/Common/Bin/oryn doctor
  ~/OrynSDK/OrynSDK/Common/Bin/oryn run ~/OrynSDK/OrynProjects/Kernel-5/Project.oryn

Default Windows QEMU search paths:

  /mnt/c/Program Files/qemu/qemu-system-x86_64.exe
  /mnt/c/Program Files/QEMU/qemu-system-x86_64.exe
  /mnt/c/Oryn/Tools/QEMU/qemu-system-x86_64.exe
  /mnt/c/msys64/ucrt64/bin/qemu-system-x86_64.exe
  /mnt/c/msys64/mingw64/bin/qemu-system-x86_64.exe

Default Windows OVMF search paths include:

  /mnt/c/Program Files/qemu/share/edk2-x86_64-code.fd
  /mnt/c/Program Files/qemu/share/OVMF_CODE.fd
  /mnt/c/Program Files/QEMU/share/edk2-x86_64-code.fd
  /mnt/c/Oryn/Tools/OVMF/OVMF_CODE.fd
  /usr/share/OVMF/OVMF_CODE.fd

You can override OVMF with either a WSL path or a Windows path:

  ORYN_OVMF_PATH
  ORYN_OVMF_WINDOWS_PATH

OrynWsl 0.4.0 image output
---------------------------
The image command creates a real raw disk image with one MBR partition.
That partition is an EFI System Partition containing a FAT32 filesystem.

Output files under OrynProjects/Kernel-5/Output:

  ESP/
    Staging folder for the same boot files.

  Kernel-5.img
    Raw boot disk image.
    MBR partition type: 0xEF EFI System Partition.
    Filesystem: FAT32.

The FAT32 partition contains:

  /EFI/BOOT/BOOTX64.EFI
  /SYSTEM/KERNEL-4/KERNEL.ELF

The kernel remains a pure x86_64 ELF executable.
BOOTX64.EFI opens the OS-named kernel ELF from the FAT32 partition, validates it as an ELF64 x86_64 executable, copies the ELF load segments, prepares the user-selected OrynBootInfo v6 fields, exits UEFI boot services, places the BootInfo pointer in RDI, and jumps to the ELF entry address. Use ./Oryn.sh OSName to ask the kernel/OS name first; that name is saved in Project.oryn and reused to name Build/<OSName>.elf and the staged kernel image.

OrynBootInfo v6 handoff
-----------------------
Kernel-5 now receives a pointer to OrynBootInfo:

  void KernelStart(const OrynBootInfo* bootInfo)

The loader always fills:

  Signature
  Version
  Size
  Flags
  BootLoaderName
  KernelName

The user can choose whether the loader also passes:

  Kernel physical base/size
  MemoryMap pointer/count/entry-size/version
  Plain linear framebuffer base/size/width/height/pitch/bytes-per-pixel/pixel-format, if available
  RSDP pointer, if ACPI is available

The kernel proves the handoff by printing:

  PASS: BootInfo received.
  Memory map entries: ...
  Framebuffer: ... or not supplied
  RSDP: ... or not supplied


UEFI BootInfo questionnaire
---------------------------
Kernel-5 can now create numbered BootInfo variants under:

  OrynProjects/Kernel-5/Kernel/<number>

Run the questionnaire with:

  ./Oryn.sh bootinfo

The questionnaire asks whether BOOTX64.EFI may pass each available UEFI BootInfo item:

  1. Kernel physical range
  2. UEFI memory map
  3. Linear framebuffer
  4. ACPI RSDP pointer

The package includes Kernel/1 as the default full BootInfo selection.

From 0.1.2 onward, the questionnaire checks existing numbered variants before writing a new one.
If the same BootInfo answers already exist, Oryn selects the existing Kernel/<number> folder instead of creating a duplicate.
Only a new unique BootInfo selection creates the next numbered folder, for example:

  OrynProjects/Kernel-5/Kernel/2/Include/OrynBootInfoSelection.h
  OrynProjects/Kernel-5/Kernel/2/BootInfoSelection.txt

The currently selected variant number is stored in:

  OrynProjects/Kernel-5/Kernel/Selected.txt

The selected header is included by both the UEFI loader build and the Kernel-5 build.
After the questionnaire, Oryn asks whether to build, image, and run the selected variant immediately.


0.1.2 duplicate-selection behavior
----------------------------------
The bootinfo command now reads existing Kernel/<number>/Include/OrynBootInfoSelection.h files
before creating a new numbered folder. If the answers match an existing variant, Oryn updates
Kernel/Selected.txt to that number and reports that the existing matching variant was selected.



OrynWsl 0.5.39 VMSettings questionnaire
--------------------------------------
Use this command from the workspace root to set the VM profile that `run` will use:

  ./Oryn.sh VMSettings

The questionnaire saves values in the project `[Run]` section:

  VM=QEMU
  FormatVM=yes
  DiskFormat=raw
  StorageInterface=ide
  Memory=512M
  CPU=qemu64
  SMP=4
  PIC=on
  APIC=on
  APIC2=on
  HPET=on
  Display=none

`FormatVM=yes` recreates the raw FAT32 VM disk image during `run`.
`FormatVM=no` reuses the existing image if it already exists.

The native run stage now uses these values instead of hardcoded defaults.
For example, Memory changes QEMU `-m`, SMP changes QEMU `-smp`, HPET changes `-machine q35,hpet=on/off`, and APIC/APIC2 changes the QEMU CPU feature list.
The same hardware choices are also passed into the kernel build as VMSettings macros, so BootReport expects proof markers only for the enabled PIC/APIC/APIC2/HPET/SMP profile.

OrynWsl 0.4.0 run output
-------------------------
Oryn starts Windows QEMU with the raw FAT32 disk image, not QEMU's synthetic fat:rw folder backend.

The run writes serial output live to the WSL terminal and writes debug-port output to:

  ~/OrynSDK/OrynProjects/Kernel-5/Output/Debug.log

It then uses QEMU isa-debug-exit so the run finishes and the debug log is printed.

  Toolchain: clang + lld

  PASS: BootInfo received.
  Memory map entries: ...

  Virtual memory: starting
  Current CR3: 0x...
  New PML4: 0x...
  Virtual memory: active

  Requesting QEMU debug-exit success.

Boot proof notes
----------------
After ./Oryn.sh run, Oryn writes these files under OrynProjects/Kernel-5/Output:

  Debug.log
    Raw QEMU debug-port output from BOOTX64.EFI and the Kernel-5 kernel.

  BootReport.txt
    Pass/fail boot report with QEMU path, OVMF path, FAT32 disk image path,
    QEMU exit code, loader stage checks, BootInfo checks, kernel-entry checks,
    and the captured debug output.

A passing boot should show:

  Result: PASS
  Loader started: PASS
  BootInfo allocated: PASS
  BootInfo memory map captured or intentionally omitted: PASS
  Kernel entered: PASS
  Kernel received BootInfo: PASS
  Kernel requested QEMU debug-exit: PASS

  C:\Users\daves\AppData\Local\Temp\OrynWSL

Override from WSL if required:

  ./Oryn.sh bootinfo show

  ./Oryn.sh bootinfo select 1

  ./Oryn.sh bootinfo compare 1 2

0.2.0 Kernel BootInfo validation and memory-map parsing
-------------------------------------------------------
OrynWsl 0.2.0 adds kernel-side validation for the OrynBootInfo v6 handoff.
The kernel now checks signature, version, size, unknown flag bits, selected-field rules,
and the basic safety of each supplied pointer/count pair before using BootInfo data.

Kernel-5 now has small kernel-owned modules for this work:

  OrynProjects/Kernel-5/Include/KernelBootInfo.h
  OrynProjects/Kernel-5/Include/KernelMemoryMap.h
  OrynProjects/Kernel-5/Source/BootInfo/
  OrynProjects/Kernel-5/Source/Memory/

When the selected BootInfo variant includes the UEFI memory map, Kernel-5 copies it into a
kernel-owned static memory map and prints a summary by class:

  Usable
  Reserved
  Bootloader reclaim
  ACPI reclaim
  ACPI NVS
  MMIO
  Runtime
  Bad
  Kernel reserved

This version does not add the physical memory allocator yet. It proves the map can be
trusted and interpreted first. If a selected variant does not include the memory map,
the kernel reports that memory services and the physical allocator are unavailable and
continues to halt cleanly.


0.2.1 BootInfo selection header compatibility fix
--------------------------------------------------
OrynWsl 0.2.1 fixes older numbered Kernel-5 BootInfo variant folders that were
created before ORYN_BOOTINFO_SELECTION_MASK existed. The kernel now derives the
selection mask from the individual ORYN_BOOTINFO_WANT_* values when an older
variant header does not define the mask.

This allows existing Kernel/2, Kernel/3, and later user-created variants to build
without deleting or recreating them.


0.3.0 Kernel-3 physical memory allocator
----------------------------------------
OrynWsl 0.3.0 keeps the allocator work in Kernel-3 and adds the first real kernel
memory service: a physical 4 KiB page allocator built from the parsed UEFI memory map.
When updating from Kernel-2, the launcher migrates unique old BootInfo variants into
Kernel-3 before removing the generated Kernel-2 project folder.

New files:

  OrynProjects/Kernel-3/Include/KernelPhysicalMemory.h
  OrynProjects/Kernel-3/Source/Memory/KernelPhysicalMemory.c
  OrynProjects/Kernel-3/Source/Memory/KernelPhysicalMemoryPrint.c

When the selected BootInfo variant includes the memory map, Kernel-3 now prints allocator
proof after the memory summary:

  Physical memory allocator: available
  Page size: 4096
  Total usable pages
  Tracked free pages
  Used pages
  Low pages held back
  Untracked usable pages
  Test alloc page 1
  Test alloc page 2
  Test free page 1
  Test alloc page 3

The allocator only uses pages classified as usable by the kernel-owned memory map.
It keeps the first 1 MiB out of allocation, does not use bootloader reclaim pages yet,
and respects the kernel physical range by relying on the earlier Kernel reserved
classification step.

If the selected BootInfo variant does not include the memory map, Kernel-3 reports:

  Memory map selected: no
  Physical allocator unavailable.
  Continuing without memory services.

Next intended steps are virtual memory/page-table foundation, then a kernel heap.


0.3.1 allocator boot report cleanup
-------------------------------------

OrynWsl 0.3.1 cleans the Kernel-3 physical allocator boot proof. The stale
"Physical allocator unavailable until the next allocator step" line has been
removed now that the allocator exists. The allocator now prints one full
summary before the self-test, then a compact final allocator state after the
self-test. Page count lines include KB as well as MB so small reserved regions,
such as the low-memory hold-back, are visible in the serial report.


0.4.0 Kernel-5 virtual memory foundation
-----------------------------------------
OrynWsl 0.4.0 moves the default project to Kernel-5 and adds the first
kernel-owned x86_64 page-table foundation. This is deliberately not a heap,
not a higher-half kernel, not user mode, and not a scheduler.

New files:

  OrynProjects/Kernel-5/Include/KernelVirtualMemory.h
  OrynProjects/Kernel-5/Source/Memory/KernelVirtualMemory.c
  OrynProjects/Kernel-5/Source/Memory/KernelVirtualMemoryPrint.c

Kernel-5 now detects the current CR3, allocates a kernel-owned PML4 and child
page tables from the 0.3.x physical page allocator, identity-maps the required
low/kernel memory, maps BootInfo and the BootInfo memory-map storage safely,
and maps the framebuffer only when the selected BootInfo profile supplies one.
It then switches CR3 to the new kernel-owned PML4.

Expected virtual-memory proof lines include:

  [KERNEL] Virtual memory: starting
  [KERNEL] Current CR3: 0x...
  [KERNEL] New PML4: 0x...
  [KERNEL] Identity mapped kernel range: ...
  [KERNEL] Identity mapped BootInfo: ...
  [KERNEL] Identity mapped memory map: ...
  [KERNEL] Framebuffer mapping: selected/not selected
  [KERNEL] Virtual memory: active

Kernel-5 is now the default project. The launcher migrates unique generated
Kernel-3 BootInfo variants into Kernel-5, preserves the selected variant when
possible, and removes generated Kernel-3 after Kernel-5 is available.

0.5.18 BootInfo handoff checksum
----------------------------------

OrynWsl 0.5.18 adds a shared CRC32 handoff checksum to the BootInfo ABI.
The UEFI loader seals OrynBootInfo after the final memory map has been copied
and before ExitBootServices. The kernel copies OrynBootInfo into kernel-owned
storage, verifies the checksum, and only then initializes framebuffer/font
console services or consumes memory-map data.

Expected proof lines include:

  [BOOT] PASS: BootInfo checksum sealed before kernel handoff.
  [KERNEL] PASS: BootInfo checksum OK: loader handoff data verified.


Kernel layout configuration
---------------------------
Project.oryn may contain a [KernelLayout] block:

  KernelPhysicalBase=0x4000000
  KernelVirtualBase=0xFFFFFFFF80000000

OrynBuild passes these values to Kernel.ld. The ELF PT_LOAD segment is copied to the physical base while the ELF entry and symbol addresses use the chosen virtual base. The UEFI x64 loader prepares a temporary identity plus higher-half/chosen virtual map before jumping to the kernel virtual entry.


0.5.25 kernel command line and boot configuration
-------------------------------------------------
Project.oryn may contain a [BootConfiguration] block:

  [BootConfiguration]
  CommandLine=oryn.boot=normal oryn.log=serial

The launcher flow is now:

  ./Oryn.sh OSName
    -> Headless
    -> BootConfig
    -> BootInfo

BootConfig shows the saved command line as the default, saves the answer back
to Project.oryn, and then continues to the BootInfo questionnaire. OrynBuild
emits the saved value into the generated OrynBootTarget.h. BOOTX64.EFI copies
it into OrynBootConfigurationBlock inside OrynBootInfo ABI v7 before sealing
the handoff checksum. The kernel validates and prints the block before using
later boot configuration.

Expected proof lines include:

  [BOOT] PASS: Boot configuration block prepared.
  [KERNEL] PASS: Boot configuration block received.
  [KERNEL] PASS: Kernel command line received.

0.5.26 x64 IDT
  Kernel startup now installs a target-owned 256-entry x86_64 IDT before BootInfo consumers and virtual-memory work. CPU exceptions 0-31 print vector, error code, RIP, CS, RFLAGS, and CR2 for page faults.

0.5.28 x64 GDT runtime call fix
- The UEFI x64 SDK target now owns a kernel GDT/TSS path.
- KernelStart loads the kernel-owned GDT before installing the IDT.
- The GDT contains null, kernel code/data, user code/data placeholders, and a 64-bit TSS descriptor.
- The TSS provides an exception IST stack used by CPU exception gates.
- BootReport checks GDT, TSS, and IDT proof markers.

0.5.28 GDT runtime proof fix
----------------------------
The kernel entry path now calls the SDK target GDT/TSS installer before the IDT installer. This ensures runtime logs contain the GDT and TSS proof markers required by BootReport. BootReport failure hints now report missing GDT markers even when the kernel reached QEMU debug-exit success.

0.5.29 PIC, APIC2/x2APIC, and HPET proof
---------------------------------------------
Kernel-5 now calls target-owned UEFI x64 hardware support for the early interrupt/timer foundation:

- KernelCpu detects CPUID local APIC, APIC2/x2APIC, TSC-deadline, invariant TSC, and vendor data.
- KernelPic remaps the 8259 PIC to 0x20-0x2F and masks both PICs for APIC handoff.
- KernelApic enables the local APIC, prefers APIC2/x2APIC MSR mode, and runs a masked APIC timer countdown probe.
- KernelHpet walks ACPI from BootInfo RSDP, validates checksums, finds the HPET table, enables the main counter, and verifies the counter advances.
- The run command exposes HPET and x2APIC through QEMU.

Expected proof lines include:

  [KERNEL] PASS: CPU APIC2/x2APIC feature present.
  [KERNEL] PASS: PIC remapped to vectors 0x20-0x2F.
  [KERNEL] PASS: PIC masked/disabled for APIC handoff.
  [KERNEL] PASS: APIC2/x2APIC mode enabled.
  [KERNEL] PASS: APIC timer counter moved in masked probe.
  [KERNEL] PASS: HPET counter advanced in probe.


0.5.30 Interrupts from PIC upward
----------------------------------
Kernel-5 now proves real interrupt delivery in controller order:

- The IDT dispatch path initializes a 256-vector handler table and per-vector counters.
- The PIC path remaps the 8259 to 0x20-0x2F, unmasks IRQ0, programs PIT channel 0 as a one-shot source, receives vector 0x20 through the IDT common stub, sends PIC EOI, and masks the PIC again.
- The APIC path then enables local APIC/APIC2 and arms a one-shot local APIC timer interrupt through vector 0xEE.
- The shared dispatcher counts both interrupts and prints PIC/APIC EOI proof markers.

Expected proof lines include:

  [KERNEL] PASS: Interrupt dispatcher initialized.
  [KERNEL] PASS: PIC IRQ0 interrupt fired through IDT dispatch.
  [KERNEL] PASS: PIC EOI path executed.
  [KERNEL] PASS: APIC timer interrupt fired through IDT dispatch.
  [KERNEL] PASS: APIC EOI path executed.
  [KERNEL] PASS: Interrupts work from PIC upward through APIC/APIC2.

0.5.31 SysCalls: Get, Set, Event message packets
------------------------------------------------
Kernel-5 now initializes the common internal syscall core before the controller interrupt proofs.

Internal kernel syscalls are exactly:

  SysCallGet
  SysCallSet
  SysCallEvent

Each call accepts an OrynSysCallPacket message packet. Platform compatibility layers translate external ABI numbers into those three packet calls:

  Common/Kernel/Include/LinuxSysCall.h
  Common/Kernel/Include/MSSysCall.h

The UEFI x64 target owns only the receiving interrupt vectors:

  0x80 LinuxSysCall compatibility vector
  0x81 MSSysCall compatibility vector

Unknown platform syscall numbers are not fatal. They are translated into a compatibility SysCallEvent packet and printed as DEBUG output so the missing syscall can be implemented later.

Expected proof lines include:

  [KERNEL] PASS: SysCall core initialized.
  [KERNEL] PASS: SysCall message packet ABI ready.
  [KERNEL] PASS: SysCallGet packet handled.
  [KERNEL] PASS: SysCallSet packet handled.
  [KERNEL] PASS: SysCallEvent packet handled.
  [KERNEL] PASS: LinuxSysCall translator registered.
  [KERNEL] PASS: MSSysCall translator registered.
  [KERNEL] PASS: Linux syscall vector 0x80 received and translated.
  [KERNEL] PASS: MS syscall vector 0x81 received and translated.
  [KERNEL] PASS: Unknown syscall debug logging path executed.
  [KERNEL] PASS: SysCalls use Get/Set/Event message packets.
  [KERNEL] PASS: Platform syscalls translate into Get/Set/Event packets.

0.5.33 PCI Discovery
---------------------
Kernel-5 now initializes target-owned PCI discovery after the interrupt/timer/syscall proof chain and before virtual-memory allocator work.

The PCI discovery path does the following:

- validates ACPI from the BootInfo RSDP,
- finds the ACPI MCFG table,
- captures the first PCIe ECAM segment descriptor,
- scans all PCI buses 0-255,
- scans every device slot 0-31,
- scans every function 0-7,
- reads vendor/device/class/subclass/progIF/header/BAR0/IRQ metadata,
- counts bridge, storage, network, and display controller classes,
- prints the first recorded PCI devices for boot diagnostics,
- keeps discovery target-owned under UEFI/X64 KernelSupport.

Expected proof lines include:

  [KERNEL] PCI: discovery starting.
  [KERNEL] PASS: PCI ACPI MCFG table discovered.
  [KERNEL] PASS: PCIe ECAM descriptor captured.
  [KERNEL] PASS: PCI config mechanism #1 responded.
  [KERNEL] PASS: PCI bus/device/function scan completed.

OrynWsl 0.5.39 VMSettings CPU safety

CPU=host is not valid for the current Windows QEMU from WSL runner because QEMU requires hardware acceleration for the host CPU model. The VMSettings questionnaire now saves CPU=max instead when host/native is entered, and the run path also resolves stale CPU=host projects to CPU=max before launching QEMU. The BootReport now treats a QEMU pre-boot command rejection as a pre-boot failure and skips loader/kernel checks instead of printing a wall of unrelated FAIL lines.

The OSName questionnaire now continues into VMSettings before BootConfig and BootInfo so VM format, memory, CPU, SMP, PIC, APIC, APIC2, HPET, and display settings are refreshed during the normal setup flow.

OrynWsl 0.5.41 Kernel screen scrolling
--------------------------------------
Kernel-5 now uses a real kernel-screen scrollback buffer instead of only shifting framebuffer pixels upward when the display fills.

Implemented behaviour:
- the console stores printed characters as scrollback cells,
- each scrollback cell keeps its foreground colour,
- framebuffer and VGA fallback screens are redrawn from the selected scroll offset,
- line scrolling is available through KConsole.ScrollUpLines and KConsole.ScrollDownLines,
- page scrolling is available through KConsole.PageUp and KConsole.PageDown,
- KConsole.ScrollToBottom returns to the live output tail,
- framebuffer mode draws a right-side scrollbar when scrollback is larger than the visible screen,
- the BootReport checks the scrolling proof markers.

Expected proof markers:

[KERNEL] PASS: Kernel screen scrollback buffer initialized.

OrynWsl 0.5.41 BootReport debug-log reader fix
-----------------------------------------------
The QEMU Debug.log reader now uses a 1 MB heap buffer instead of a 64 KB stack buffer. This stops long successful boots from being falsely reported as FAIL when later virtual-memory, SMP, halt, and QEMU debug-exit proof markers appear after the first 64 KB of output.

SMP discovery proof markers are also printed immediately during the pre-virtual-memory ACPI/MADT discovery stage, so BootReport can verify RSDP, checksum, MADT, and CPU topology before the verbose BootInfo summary grows the log.

OrynWsl 0.5.42 Kernel screen double buffering

The kernel console now renders to an off-screen buffer before presenting to the visible screen. Framebuffer mode uses a kernel-owned pixel back buffer, and VGA fallback uses a shadow text buffer before copying the completed text frame to 0xB8000. Scrollback redraws, coloured cells, line/page scrolling, and normal character output all go through the same back-buffer/present path.

Boot proof markers:

[KERNEL] PASS: Kernel screen back buffer allocated.
[KERNEL] PASS: Kernel screen renders into back buffer first.
[KERNEL] PASS: Kernel screen presents completed frame to visible output.
[KERNEL] PASS: Kernel screen double buffering implemented.


OrynWsl 0.5.43 Kernel screen line-buffered flip

The kernel console still uses a framebuffer/VGA double buffer, but normal printable characters now update only the back buffer. The visible buffer is presented after a whole line is committed by newline or automatic wrap, and still presents immediately for clear, scroll, page-scroll, scroll-to-bottom, and full redraw operations.

Expected proof markers:

[KERNEL] PASS: Kernel screen defers visible flip while line is being written.
[KERNEL] PASS: Kernel screen flips after completed line.
[KERNEL] PASS: Kernel screen line-buffered double buffering implemented.


OrynWsl 0.5.45 Interactive QEMU scroll testing
-----------------------------------------------
When [Run] Display is set to sdl/windowed instead of none, Oryn now treats the run as an interactive screen-test session.

In interactive display mode:
  - QEMU is launched without the isa-debug-exit device.
  - The kernel does not request QEMU debug-exit at the end of boot.
  - The VM remains open in the QEMU window so the kernel screen and scrollback can be tested manually.
  - Close the QEMU window when testing is complete; Oryn then copies Debug.log and writes BootReport.txt.

In headless mode:
  - Display=none still uses isa-debug-exit.
  - The kernel requests debug-exit success.
  - Automated BootReport pass/fail behaviour remains unchanged.

Use:
  ./Oryn.sh VMSettings

Then answer No to the headless/display question, or set:
  [Run]
  Display=sdl


OrynWsl 0.5.45 Fast interactive screen refresh
------------------------------------------------
Kernel screen double buffering is now line/scroll optimized. Printable characters update the kernel-owned back buffer only; the visible framebuffer is presented after a completed line. When the live view reaches the bottom of the screen, the console uses a fast scroll path instead of redrawing every visible cell for every line. In interactive Display=sdl mode, QEMU serial is connected to a null sink so the WSL terminal is not flooded while the QEMU window is being used for manual scrolling tests. Debug output is still captured through QEMU debugcon in Output/Debug.log.

The physical allocator tracking capacity was increased to cover the normal 2G VM profile without reporting that the static page tracker was full. The allocator now prints a PASS marker when all usable pages are tracked.


OrynWsl 0.5.46 Early SMP startup

SMP is now started at the earliest safe point in the UEFI x64 kernel boot path.
The order is now GDT/IDT/syscalls, CPU/PIC/APIC/APIC2 setup, then SMP discovery and AP startup.
Application processors are started and parked before HPET proof, PCI discovery, framebuffer console setup, BootInfo summary printing, physical memory setup, and virtual-memory proof.
BootReport now verifies the early-SMP markers:
  [KERNEL] SMP: starting early after APIC/APIC2 enable.
  [KERNEL] PASS: SMP AP startup moved before PCI/HPET/console/memory proof.
  [KERNEL] PASS: SMP AP startup completed before PCI/HPET/console/memory proof.
